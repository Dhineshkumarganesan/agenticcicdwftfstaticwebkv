🚀 Intent-Driven Agentic CI/CD

How Natural Language Drives Your Entire Pipeline — from Scaffolding to Deployment

The Problem with Traditional CI/CD

Traditional pipelines are rigid. Every build, test, and deployment step must be explicitly defined by a developer — making it hard to scale across projects or adapt to changing requirements.

Intent-driven CI/CD solves this by letting you declare what you want to deploy, and letting the pipeline figure out how to do it automatically.

The Pipeline Flow

📋 contract.yml → 🤖 Copilot Agent → 🏗️ Terraform Scaffold → ✅ CI Guardrails → ☁️ Azure Deploy → 🌐 Live Site

The developer only writes contract.yml — everything else is automated.

Two-Repo Architecture

Factory Template — the engine that provides all reusable patterns, agents, and guardrails.

Consumer Repo — the driver that declares business intent. The factory machinery does the rest.

Each consumer repo gets its own isolated Azure identity (OIDC), its own Terraform state backend, and its own deployment environments.

Key Technologies

GitHub Actions Azure Terraform OIDC Auth GitHub Copilot contract_lint.py Progressive Deployment Azure Static Website Terraform State Locking

Lessons Learned

  • Use --auth-mode login with OIDC — never store storage keys
  • Assign Storage Blob Data Contributor via Terraform so it recreates daily
  • Use -lock=false on CI terraform plan to avoid state lock conflicts
  • Azure blob leases don't auto-release on pipeline cancellation — break them manually
  • SHA pinning policy enforcement via contract_lint.py catches supply-chain drift early
